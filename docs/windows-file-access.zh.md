# Windows 文件写入与删除问题

[English](windows-file-access.md) · 简体中文

## 先确认失败的是哪种操作

DeepShian 将文件操作交给 DeepSeek Harness。在 Windows 上，原生文件编辑工具和 PowerShell 命令走的是不同的权限路径：

```text
原生文件工具 -> Harness 文件策略检查 -> 宿主文件操作
PowerShell   -> Harness 进程沙箱     -> Windows 受限子进程
```

`edit` 成功，不代表命令行一定能写入或删除同一文件。受限子进程提示拒绝访问，也不能单凭这一条就认定当前 Windows 账号没有文件权限。

当前插件只有“只读”和“工作区写入”两种模式。模型建议切换会话级“完全权限”，并不符合当前插件的界面；单次经过审批的工具提权是另一项操作。

## 修改权限之前先检查

1. 记录准确的目标路径、失败工具、错误和版本。以最新失败记录为准，不要将旧报错当作当前状态。
2. 确认使用“工作区写入”，目标位于本会话的笔记库工作区内。“只读”拒绝修改是预期行为。
3. 区分错误。`Access denied`、`Permission denied` 需要检查访问权限；`MethodInvocationNotSupportedInConstrainedLanguage` 表示 PowerShell 拒绝了某个语言或 API 操作，不能据此判定文件无法删除。
4. 诊断应同时比较普通进程和 Harness 实际受限令牌下的访问结果。普通进程可写不能代替沙箱验证。
5. 在受影响目录中使用唯一命名的临时文件，分别验证创建、覆盖、删除和清理。检查能否取得删除权限的句柄有参考价值，但不等于已经执行过删除测试。

PowerShell 诊断应遇错停止并检查结果，不能在前面的命令失败后仍报告成功。不要把 `git clean` 当成权限测试，它选择的是未跟踪文件，不是一个明确限定的测试对象。

## Harness 0.2.2-rc.1 中观察到的案例

一次 Windows 排查中，工作区根目录保留了 Harness 的工作区专用授权，但两个下层笔记目录缺少继承的授权。安装版本在根目录命中已有授权后复用了它，没有修复这些后代对象。结果是原生编辑能工作，受限子进程的写入和删除访问检查返回 Win32 5。

对明确批准的两个目录做本机局部修复后，受限令牌下的文件创建、覆盖和删除通过；同时核对了文件内容与原有权限条目的备份。这属于本机环境维护，本 fork 没有内置自动权限修复，也不能把这一案例套用到所有 Windows 拒绝访问问题。

权限变更应建立在已确认的原因、具体批准的范围，以及访问规则和完整性标签备份之上。广泛更改所有者、递归重置权限或全局关闭沙箱，不属于本插件的排查流程。

底层授权、完整性标签与恢复边界见上游 [Windows 沙箱实现说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/sandbox/sandbox-windows-acl/README.zh.md)。反馈问题时提供最小化、已隐去敏感信息的错误及版本，不要上传整份私人会话或笔记库。
